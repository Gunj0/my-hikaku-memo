# 非機能要件定義

## 1. 文書の目的

本書は、現行アプリに求める品質特性、利用環境、制約、運用前提を定義する。

## 2. 対象環境

- 利用形態は Web ブラウザによる利用とする。
- PC とスマートフォンの双方からの利用を想定する。
- 日本語利用を前提とする。

## 3. ユーザビリティ要件

- 比較フローは 1 画面で完結し、利用者が現在位置を見失わないこと。
- 各ステップの主目的が見出しと補足文で把握できること。
- 次へ進めない場合はボタン無効化により状態が分かること。
- 重視ポイント、最高評価候補、選択済み製品など重要情報が視覚的に識別できること。

## 4. レスポンシブ要件

- モバイルでは横幅制約を前提とした表示に切り替えること。
- デスクトップでは比較しやすい表形式を優先すること。
- 進捗表示はモバイルで横スクロール可能とし、全ステップへのアクセス性を維持すること。

## 5. 性能要件

- 画面操作に対する応答は利用者が待機を意識しない範囲であること。
- ステップ移動、スコア入力、候補選択など主要操作はクライアント側で即時反映されること。
- 現行想定の少量データでは、サーバー往復なしで画面更新が完結すること。
- ホームの公開メモ抽出は、公開メモの総件数に比例して劣化しないこと。更新の新しい順に一定件数（現行 300 件）へ絞った母集団からランダムに選び、走査量を件数によらず一定に保つ。母集団より古い公開メモはホームには現れない。

## 6. 可用性・信頼性要件

- 比較フローの入力と集計はログイン有無にかかわらず利用できること。
- 保存済みメモ機能は Google OAuth と D1 に依存するが、これらが利用できない場合でも比較フロー自体は継続利用できること。
- 未保存データは編集中にブラウザの sessionStorage または localStorage へ自動退避されること。
- 自動退避データの復元は同一ブラウザ内に限定し、ストレージ消去、別端末、別ブラウザでの保持は保証しないこと。

## 7. データ保持要件

- 未保存の入力データはブラウザ実行中のメモリに加えて、同一ブラウザ内の sessionStorage または localStorage へ自動退避される。
- localStorage へ自動退避するデータは guest またはログインユーザー単位で分離されること。
- 利用者が明示的に保存した比較メモは D1 に永続保持する。
- 保存済みメモはログインユーザー単位で分離されること。
- 保存済みメモの既定公開状態は非公開であること。
- リセット操作により、画面上の編集中データは明示的に破棄されること。

## 8. セキュリティ要件

- 認証は Google OAuth を利用して行うこと。
- セッションは Auth.js のデータベースセッションで管理すること。
- 保存済みメモに対する取得、更新、削除は本人のアカウントに限定すること。
- 非公開メモは所有者以外から取得できないこと。
- 利用者入力は保存時と読込時にサーバー側で扱われるため、入力形式を検証すること。
- ブラウザに自動退避される編集中データは、現在の利用者スコープに一致するものだけを復元対象とすること。
- 全レスポンスに共通のセキュリティヘッダを付与すること。対象は Content-Security-Policy、X-Frame-Options、X-Content-Type-Options、Referrer-Policy、Permissions-Policy、Strict-Transport-Security とする。
- 配信経路が 2 つあるため、設定箇所も 2 つに分かれる。動的レスポンスは `next.config.ts` の `headers()`、Workers Assets が Worker を経由せず直接返す静的アセット（`/icon.png`、`/_next/static/*` など）は `public/_headers` が担う。`next.config.ts` を変更した場合は `public/_headers` も見直すこと。片方だけ直すともう片方が素通しになる。
- 静的アセット側には `form-action` / `base-uri` / `Permissions-Policy` を付与しない。素の画像・スクリプト配信に対して意味を持たないため、CSP は `frame-ancestors` のみとする。
- CSP には現状 `script-src` / `style-src` を含めない。App Router がインラインスクリプトを出力するため、nonce を配線しない限り `'unsafe-inline'` が必要になり防御にならないため。nonce 無しでも実効性のある `frame-ancestors` / `base-uri` / `object-src` / `form-action` に限定する。`script-src` まで締める場合は nonce の配線を別途行うこと。

## 9. アクセシビリティ要件

- ボタン、入力欄、チェックボックスなど基本操作要素には適切なラベルが付与されること。
- ステップ進行や選択状態は色だけに依存せず、文言やアイコンでも識別可能であること。
- キーボードで主要操作が行えることを考慮すること。

## 10. 保守性要件

- 画面全体の状態管理、ステップ UI、共通 UI を分離し、変更影響を限定できる構成であること。
- データ構造は型定義として集約し、仕様変更時に影響点を追跡しやすいこと。
- スコア集計ロジックは画面表示から読み取れる形で明確であること。

## 11. 運用・配備要件

- 開発時は Next.js 開発サーバーで動作すること。
- E2E 自動テストは Playwright を利用し、現行の実行対象ブラウザは Chromium のみとすること。
- E2E は未ログイン・ログイン済みの両方を対象とし、ログイン状態はローカル D1 に作成したセッションと Cookie で再現すること（Google OAuth を E2E から実行しないこと）。
- 本番配備は OpenNext を用いた Cloudflare 環境を前提とすること。
- 公開対象ページでは canonical、Open Graph、Twitter Card、robots.txt、sitemap.xml、構造化データの整合性を維持すること。
- ログイン後の管理画面や編集画面など内部向けページは noindex を維持すること。
- 生成される公開 URL は Cloudflare ランタイムの NEXT_PUBLIC_SITE_URL または SITE_URL を基準とすること。
- ローカル開発や preview では loopback URL に限りリクエスト URL を補助的に利用できること。
- 運用環境では公開 URL を NEXT_PUBLIC_SITE_URL または SITE_URL に設定し、未設定や loopback URL のまま動作させないこと。
- Cloudflare 側に Google OAuth 用 secret と D1 binding を設定すること。
- 環境定義変更時には Cloudflare 型定義の再生成が必要であること。

## 12. 技術制約

- フロントエンドは Next.js と React を前提とする。
- UI 実装は既存の共通 UI コンポーネント群を利用する。
- 認証は Auth.js を前提とする。
- 永続化は Cloudflare D1 を前提とする。
- サーバー側の保存処理は App Router の Route Handler で実装する。
