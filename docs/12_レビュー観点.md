# レビュー観点

## 1. 目的

変更をレビューするときに毎回ゼロから観点を組み立てないための、汎用チェックリストである。

`.github/skills/code-review/SKILL.md` がレビューの**手順**（対象特定 → 支配点発見 → findings 作成）を定めるのに対し、本書は**何を疑うか**の一覧を扱う。手順は SKILL、観点は本書、という分担にする。

網羅を目的にしない。変更が触れた領域の節だけを読み、当たらない観点は飛ばす。

## 2. 使い方

1. 変更差分から、触れた領域を特定する（下の対応表）
2. 該当する節の観点を当てる
3. 当たった観点は「再現条件・壊れる挙動・根拠ファイル」の 3 点セットで findings 化する

| 変更した領域                  | 読む節              |
| ----------------------------- | ------------------- |
| どんな変更でも                | 3, 4, 11            |
| API・サーバー処理             | 5, 6, 7             |
| DB スキーマ・永続化           | 6, 7                |
| 認証・権限・公開範囲          | 5, 7                |
| 画面・コンポーネント          | 8, 9                |
| クライアント状態・自動保存    | 9                   |
| メタデータ・URL・SEO          | 10                  |
| ビルド・デプロイ・環境変数    | 11                  |

## 3. 基本観点（全変更共通）

- **境界値**: 0 件、1 件、上限ちょうど、上限 +1、空文字、null / undefined、負値
- **失敗経路**: 成功時だけでなく、失敗時に何が残るか。中途半端な状態で終わらないか
- **並行実行**: 同じ操作が同時に 2 回走ったらどうなるか。とくに採番、カウンタ、一意制約
- **べき等性**: 同じリクエストを 2 回投げたときに副作用が 2 回起きてよいか
- **コメントと実装の一致**: コメントが実装より強い保証を主張していないか。型定義の値域コメントが実際のスキーマと合っているか
- **既存データ**: この変更を本番の既存データに当てたら壊れるものはないか

## 4. 変更の妥当性

- 依頼された範囲を超えて広がっていないか。無関係な整形やリファクタが混ざっていないか
- 逆に、依頼の一部だけ実装して残りが黙って落ちていないか
- 既存の抽象で表現できたものを新しく作り直していないか
- 同じ判断が 2 か所以上に複製されていないか（値域、上限値、正規化ルール、予約語）

## 5. 認証・権限・公開範囲

- 認証チェックが**個別のハンドラに書かれている**か、**構造的に強制されている**か。前者は書き忘れが起きる
- 取得・更新・削除が本人所有のリソースに限定されているか。`WHERE id = ?` だけで `AND user_id = ?` が抜けていないか
- 公開／非公開のフラグが、一覧・詳細・検索・sitemap・メタデータ**すべての読み取り経路**で一貫して効いているか。1 経路でも抜けると漏れる
- 「見つからない」と「権限がない」を外部に区別させていないか（存在の推測を許す）
- 識別子が連番のとき、列挙されて困る情報がないか。件数・作成順序も情報である
- 管理者・所有者だけの UI が、サーバー側でも同じ条件で守られているか（表示を隠すだけになっていないか）
- 認証が使えない状況でも、認証不要の機能は継続できるか

## 6. データ永続化

- スキーマ変更に対応する migration があるか。既存行がある状態で流せるか（NOT NULL 列の追加、制約の後付け）
- 一意制約と、その値を生成するコードの整合。`MAX(x) + 1` 系の採番は競合する
- 書き込みが複数文に分かれているとき、途中で失敗したらどうなるか。トランザクション／batch が要らないか
- 更新の成否判定が「影響行数」で表現されているか。DB レベルのフラグで代用していないか
- 読み取り時に、保存された値がスキーマを満たさない場合の扱いが決まっているか（古い形式のデータ）
- 削除時の関連データ。外部キーの ON DELETE、参照している ID の整合
- クエリに上限があるか。データが 100 倍になっても成立するか
- インデックスが、実際に発行されるクエリの WHERE / ORDER BY と一致しているか

## 7. API 契約

- リクエスト／レスポンスのスキーマが、呼び出し側の期待と一致しているか
- バリデーションがサーバー側にあるか。クライアント側のクランプだけに依存していないか
- 受理する値域が、ドメインの値域より広くなっていないか。広い場合、黙って丸めるのか 400 で弾くのか
- エラーが、ステータスコードとボディの両方で表現されているか。クライアントが分岐できるか
- 想定外の例外が 500 として漏れていないか。ユーザーに何が起きたか伝わるか
- 書き込み系にコスト上限があるか（件数上限、サイズ上限、レート制限）
- 破壊的変更のとき、既存クライアント（キャッシュ済み JS、開いたままのタブ）が壊れないか

## 8. UI・アクセシビリティ

- ローディング、空状態、エラー状態が揃っているか
- 主要操作がキーボードで到達できるか。フォーカス順序が破綻していないか
- 状態表現が色だけに依存していないか（アイコン・テキストの併用）
- モバイルとデスクトップの両方で成立するか。横幅制約下でテーブルや進捗表示が操作できるか
- 破壊的操作に確認があるか。確認 UI が他の箇所と揃っているか
- 日本語入力の IME 変換確定 Enter で、意図しない送信・追加が起きないか
- 操作フローのステップを増やさずに達成できないか

## 9. クライアント状態・永続化

- ストレージのキーが、ユーザー・ゲスト・対象 ID の単位で衝突しないか
- ログイン前後でスコープが切り替わったとき、前のスコープのデータが漏れて復元されないか
- 復元したデータが現在のスキーマ・上限値を満たすか。満たさない場合に正規化されるか
- リセット、直接遷移、読み込み直後の自動保存が、新しい状態を古い状態で上書きしないか
- サーバー状態とクライアント状態の対応（URL、編集中データ、選択中リソース）がずれないか
- SSR とクライアントで初期レンダリング結果が一致するか（hydration）

## 10. URL・メタデータ・SEO

- canonical、Open Graph、Twitter Card、構造化データ、robots.txt、sitemap.xml が同じ URL を指しているか
- 正規化（大文字小文字、末尾スラッシュ、旧パス）がリダイレクトで一意に寄せられているか
- 非公開・内部向けページに noindex が付いているか。逆に公開ページから外れていないか
- 薄いページ（中身が 0 件）を index させる条件と、sitemap への掲載条件が一致しているか
- 基準 URL が本番で正しく解決されるか。未設定時に loopback やリクエストヘッダへフォールバックしないか
- 動的セグメントがルート直下を占有する場合、新しい静的パスの追加が既存 URL を奪わないか（予約語）
- URL を変更したとき、既存の共有リンクが切れないか

## 11. ビルド・CI・運用

- CI が実際に検証しているものと、リポジトリが持っているテストが一致しているか。**テストがあるのに CI で走っていない**のが最も起きやすい抜け
- lint、型チェック、ユニットテスト、ビルドのうち、どれが落ちてもマージできない構成になっているか
- 新しいコマンド・スクリプトが CLAUDE.md / README に反映されているか
- 環境変数の追加が、ローカル・preview・本番の 3 面すべてに反映されているか
- 秘密情報がリポジトリに入っていないか（.gitignore の確認だけでなく、実際に追跡されていないか）
- 本番でのみ有効になる分岐（環境判定）が、本番で意図どおり動く保証があるか

## 12. パフォーマンス

- 同じデータを 1 リクエスト内で複数回取得していないか。とくにメタデータ生成と本体レンダリングの重複
- N+1 になっていないか。ループの中に問い合わせがないか
- キャッシュ方針が明示されているか。全経路を動的にする判断に理由があるか
- レスポンスに、行数に比例して膨らむインラインデータが乗っていないか
- 上限のないリストが UI・API・sitemap に露出していないか

## 13. ドキュメント

- 実装変更に対応する `docs/` または README の更新が同一変更に含まれているか
- 更新不要と判断した場合、その理由が説明できるか
- 仕様判断を伴う変更で、要件文書のほうが先に更新されているか
- コード内コメントが、変更後の実装を説明しているか（古い前提が残っていないか）

## 14. findings の書き方

各 finding は次を満たす。

- 何が壊れるかを最初に書く
- どの条件で起きるかを書く
- 根拠ファイルを示す
- 可能なら最小の修正方針か確認方法を添える

重大度の目安:

- **High**: 本番で壊れる、保存データや認証が破綻する、主要フローが進まない
- **Medium**: 特定条件で回帰する、仕様逸脱、放置するとスケール時に確実に問題化する
- **Low**: 軽微な不整合、保守性低下、限定的な UX 退行

好みの指摘と、広すぎるリファクタ要求は書かない。問題がない場合も、残るテストギャップや未実施の検証は明記する。
